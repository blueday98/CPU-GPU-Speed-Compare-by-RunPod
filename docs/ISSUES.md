# GitHub Issues 초안

개인 저장소를 만든 뒤 아래 항목을 각각 Issue로 등록한다. 운영 주소, 토큰, 개인키, 내부 IP는 공개하지 않는다.

## 1. 공식 Worker 재배포 시 GPU A/B 분기가 사라짐

**현상**

운영 컨테이너에 임시로 추가한 GPU 라우팅 파일과 환경변수가 팀의 공식 이미지 재배포 후 사라졌다. `video_analysis_gpu_ab`라는 이름은 남아 있어도 실제 실행은 OCI CPU 기본 경로가 된다.

**원인**

변경이 팀 소스와 이미지 빌드 과정에 포함되지 않고 실행 중인 컨테이너에만 존재했다.

**재발 방지 조건**

- 운영 컨테이너 직접 수정 금지
- 검증 코드는 브랜치·PR·공식 이미지로만 반영
- 배포 후 이미지 ID, 라우팅 파일, GPU 증거 파일을 자동 확인
- GPU 경로는 기본 비활성 기능 플래그로 보호

## 2. `video_analysis` 한 단계에 여러 병목이 합쳐져 원인 파악이 어려움

**현상**

Grafana에는 `video_analysis` 하나만 표시되지만 실제로는 디코딩, 사람 검출, 자세 추론, 렌더링, 중간 영상 생성, 최종 인코딩이 포함된다.

**개선 조건**

- 최소 `decode`, `detection`, `pose`, `render`, `encode`, `transfer` 시간 기록
- 상위 6단계 계약은 유지하되 내부 세부 시간을 별도 JSON 또는 메트릭으로 노출
- 전체 시간과 내부 시간의 합계 차이도 표시

## 3. CPU와 CUDA 결과가 일부 경계 프레임에서 달라짐

**현상**

- 60fps 영상: 프레임 및 인원 수 동일, 평균 관절 차이 약 0.142px
- 트레드밀 영상: 631개 프레임 중 349번 프레임에서 CPU 2명, GPU 1명
- 트레드밀 전체 평균 관절 차이는 약 0.416px이지만 일부 관절에 큰 이상치가 있음
- GPU 반복 실행 2회는 서로 완전히 동일

**추정 원인**

CPU와 CUDA 연산의 작은 수치 차이가 탐지 임계값, 트래킹 또는 경계 관절 선택에 영향을 줄 수 있다.

**완료 조건**

- 문제 프레임의 CPU/GPU bbox, score, track ID를 시각화
- 허용 오차와 인원 수 불일치 허용 기준 결정
- 임계값 근처 결과에 대한 회귀 테스트 추가

## 4. RunPod 재시작 후 API가 자동으로 복구되지 않음

**현상**

Pod를 다시 켜면 영구 볼륨의 모델과 가상환경은 남지만 API 프로세스는 실행되지 않아 8000번 주소가 `Waiting for service to respond` 상태가 된다. HTTP 주소 또는 SSH 접속 방식도 바뀔 수 있다.

**개선 조건**

- 시작 스크립트 또는 템플릿에 API 부팅 명령 포함
- `/health` 준비 완료 후 요청 허용
- 모델·소스 해시 불일치 시 시작 실패
- 토큰을 명령 기록이나 저장소에 노출하지 않음

## 5. 짧은 영상에서는 OCI↔RunPod 전송 오버헤드 비중이 큼

**현상**

60fps 영상의 GPU 내부 분석 중앙값은 약 2.85초, NVENC는 약 0.84초지만 OCI→RunPod 전체 왕복 중앙값은 8.77초다. 약 5초가 업로드, 응답 준비, 다운로드 및 압축 등에 사용된다.

**개선 후보**

- 영상과 결과를 ZIP으로 왕복하지 않고 Object Storage 경로 전달
- 출력 영상과 JSON을 분리해 필요한 결과부터 반환
- 응답 압축 및 파일 크기 측정
- 연결 재사용과 리전 간 네트워크 지연 측정

## 6. 긴 영상에서 피처 계산이 입력 특성에 따라 실패함

**현상**

일부 긴 영상에서 stride 또는 gait 이벤트가 비어 `feature_extract`가 실패했다. 동일 영상을 다시 실행해도 재현된 사례가 있다.

**완료 조건**

- stride가 없을 때 명확한 `insufficient_data` 결과 반환
- 0으로 나누기와 잘못된 구간 assertion 방지
- 최소 프레임·보행 주기 요구사항 문서화
- 실패 영상을 회귀 테스트 입력으로 추가

## 7. 실제 6단계 파이프라인과 Grafana의 `9/9` 표시가 불일치함

**현상**

최신 파이프라인은 6개 상위 단계지만 일부 Grafana 패널은 계속 `9/9`로 표시한다.

**완료 조건**

- 단계 수를 고정값이 아니라 Job의 실제 단계 정의에서 계산
- 구버전 9단계 Job과 최신 6단계 Job을 모두 올바르게 표시

## 8. 모델 명세의 골든 품질 승인이 대기 상태임

**현상**

Runners_Feed의 `sehyeon-dcc2d7d` 모델 명세와 OCI ONNX 가중치 해시는 모두 일치한다. 명세의 `quality.golden_status`와 `quality_baseline.json`의 `approval_status`는 모두 `pending_modeler_approval`이다. 실제 배포 후보 검증은 후자의 값이 `approved`인지 검사한다.

**완료 조건**

- 모델 담당자가 골든 입력과 기대 결과를 승인
- 승인 결과와 허용 오차를 저장소에 기록
- CPU와 CUDA 경계 결과 차이를 골든 검사에 포함

## 9. 최신 모델 플러그인이 품질 승인 전이라 공식 진입점으로 활성화되지 않음

**현상**

최신 작업 처리기에는 `COACH_MODEL_ID=sehyeon-dcc2d7d`와 플러그인 파일이 포함돼 있다. 그러나 `COACH_HPE_ENTRYPOINT=/app/coach/scripts/hpe/hpe.py`가 명시되어 있어 품질 승인 전에는 기본 진입점을 실행한다. 명세의 `golden_status`도 `pending_modeler_approval`이다.

**영향**

플러그인 HPE와 기본 HPE는 공백 제외 비교에서 실행 내용이 동일하므로 기존 HPE 성능 시험이 무효가 되지는 않는다. 다만 플러그인이 공식 활성화됐다고 표현하거나 최신 모델 적용 완료로 표시하면 안 된다. 플러그인의 feature·agent 진입점도 별도 승인 대상이다.

**완료 조건**

- 모델 담당자의 골든 품질 승인 완료
- `COACH_HPE_ENTRYPOINT`와 `COACH_FEATURE_ENTRYPOINT`를 공식 플러그인 경로로 전환
- 전환 후 동일 입력으로 사이트·Grafana 검증
- 소스·모델·입력 해시와 실제 진입점 경로를 증거에 포함

## 10. CPU와 GPU 출력 인코더의 화질 동등성이 검증되지 않음

**현상**

CPU 후보는 `libx264 veryfast CRF23`, GPU는 `h264_nvenc p4 CQ23`으로 출력했다. CRF와 CQ는 인코더가 다른 별도 품질 제어 방식이므로 값 23이 같은 화질을 보장하지 않는다. 해상도·FPS·프레임 수·재생 가능 여부는 확인했지만 시각적 화질 동등성은 측정하지 않았다.

**완료 조건**

- 동일 원본과 렌더링 프레임을 기준으로 VMAF·SSIM·PSNR 측정
- 결과 영상 파일 크기와 인코딩 시간 함께 기록
- 서비스가 허용할 최소 화질 기준 합의
- 품질 기준을 만족하는 각 인코더 설정에서 처리시간 재비교
