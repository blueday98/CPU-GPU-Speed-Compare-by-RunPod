# 전체 실험 이력

이 문서는 초기 문제 발견부터 OCI CPU와 RunPod GPU의 전체 영상 분석 비교까지의 과정을 시간순으로 정리한다. 서로 다른 측정 범위의 결과를 직접 비교하지 않도록 각 단계의 포함 범위를 명시한다.
## 0. RunPod을 실험하게 된 계기

우리의 프로젝트 Runner’s Feed는 사용자가 업로드하거나 촬영한 러닝 영상을 분석하고, 논문에 근거하여 올바른 러닝 자세에 대한 피드백을 제공하는 서비스이다.  
나는 논문 조사, 피처 로직 구현, 관련 데이터 탐색을 주로 담당했다. 하지만 영상마다 촬영 조건과 데이터가 달라 분석 결과와 처리시간에도 차이가 발생했기 때문에, 영상 전처리 조건을 조정하여 처리 과정을 최적화해보고 싶다고 요청했다. 이 작업이 서버 자원과 영상 처리 인프라에 관련되어 있어 인프라 팀에 합류하게 되었다.
인프라 팀에서는 cAdvisor, Node Exporter, Prometheus, Grafana로 이어지는 모니터링 구조와 각 도구의 역할을 간단히 설명해주었다. 나는 전체 구조와 기본 개념을 파악한 뒤, 주로 Grafana 대시보드에서 영상 조건별 처리시간과 단계별 병목을 측정하고 CPU와 GPU의 성능 차이를 비교·기록하는 업무에 집중했다. GPU 성능 차이를 비교하기 위해서 사용한 것이 RunPod 이다.

## 1. 출발점: Grafana에서 병목 발견

Runner's Feed의 영상 처리 작업은 처음에는 9개 단계로 관찰됐다.

```text
입력 다운로드
→ 프레임 추출
→ 자세 추론
→ 코칭 리포트 생성
→ 프레임 렌더링
→ 영상 합성
→ 영상 인코딩
→ 결과 업로드
→ 작업 폴더 정리
```

동일 계열 입력을 두 번 실행했을 때 Celery 작업시간은 44.856초와 42.318초였다. Grafana 총 처리시간은 각각 44.745초와 42.210초로, 경계 차이는 약 0.1초였다. 당시 단계별 대표 측정은 다음과 같았다.

| 단계 | 1차 | 2차 | 평균 |
|---|---:|---:|---:|
| 입력 다운로드 | 0.127초 | 0.134초 | 0.131초 |
| 프레임 추출 | 5.632초 | 5.775초 | 5.704초 |
| 자세 추론 | 16.737초 | 14.663초 | 15.700초 |
| 리포트 생성 | 10.259초 | 9.676초 | 9.968초 |
| 프레임 렌더링 | 6.823초 | 6.846초 | 6.835초 |
| 영상 합성 | 2.830초 | 2.876초 | 2.853초 |
| 영상 인코딩 | 2.039초 | 1.951초 | 1.995초 |
| 결과 업로드 | 0.130초 | 0.125초 | 0.128초 |
| 작업 폴더 정리 | 0.080초 | 0.078초 | 0.079초 |

이 결과에서 자세 추론이 가장 큰 단일 병목이었지만, 모델 추론을 제외한 작업도 평균 약 27.9초를 차지했다. 따라서 목표를 “GPU 추론이 빠르다”가 아니라 “실제 서비스 영상 분석 전체 시간을 줄인다”로 정했다.

## 2. 입력 조건 검토

해상도, FPS, CRF를 바꿔 사이트 처리시간과 피처 성공 여부를 확인했다. 해상도와 FPS를 낮추면 처리시간은 줄었지만 stride와 수직 진폭처럼 보행 피처가 검출되지 않는 경우가 있었다.

당시 팀 논의에서 정한 촬영 기준은 다음과 같다.

- 해상도 720p
- 최소 30fps, 권장 60fps
- CRF18
- 측면 전신 촬영
- 발이 화면 밖으로 잘리거나 사람이 가려진 영상은 재촬영
- 여러 사람, 심한 흔들림·모션 블러, 어두운 환경, 비실사 영상은 거부 대상

이 기준은 모델과 피처가 계속 개발 중이므로 최종 제품 계약으로 간주하지 않는다.

## 3. RunPod GPU 환경 확인

가장 저렴한 후보였던 NVIDIA RTX 2000 Ada Generation에서 다음 환경을 확인했다.(시간당 0.24$)

```text
PyTorch 2.8.0+cu128
CUDA 12.8
cuDNN 91002
ONNX Runtime 1.26.0
CUDAExecutionProvider 사용 가능
```

사람 검출 RTMDet와 자세 추정 RTMPose ONNX 모델을 CUDA 실행 공급자로 적재했다.

## 4. 임의 입력 순수 추론 시험

영상 입출력을 제외한 임의 배열 입력으로 ONNX 계산 성능만 비교했다.

| 모델 | CPU 평균 | GPU 평균 | 배수 |
|---|---:|---:|---:|
| RTMDet | 186.019ms | 3.589ms | 51.83배 |
| RTMPose | 345.863ms | 3.136ms | 110.28배 |

이 수치는 GPU 연산 가능성을 확인한 미세 시험이다. 디코딩, 전처리, 추적, 저장, 네트워크는 포함하지 않는다.

## 5. RunPod 내부 실제 프레임 CPU/GPU 비교

약 4초, 720p·25fps 계열 영상에서 추출한 136개 프레임을 동일 코드와 모델로 실행했다.

| 항목 | CPU | GPU | GPU 향상 |
|---|---:|---:|---:|
| 사람 검출 | 18.48초 | 1.50초 | 12.32배 |
| 자세 추정 | 65.04초 | 0.74초 | 87.89배 |
| 모델 측정 합계 | 83.52초 | 2.24초 | 37.29배 |
| HPE 프로그램 전체 | 124.393초 | 9.996초 | 12.44배 |

프레임 추출 8.84초까지 포함하면 CPU 약 133.23초, GPU 약 18.84초였다. 그러나 이 비교는 RunPod 내부 CPU와 GPU의 차이이며 OCI 서비스 전체 비교가 아니다.

## 6. Grafana 측정 범위 확인

Grafana 패널은 Celery 로그를 직접 읽지 않고 PostgreSQL 작업 테이블의 다음 값을 계산했다.

```sql
completed_at - started_at
```

포함 범위는 작업 처리 시작, 입력 다운로드, 분석 파이프라인, 결과 업로드, 성공 기록이다. 브라우저의 최초 업로드, 큐 대기, 사용자 결과 다운로드는 포함하지 않는다.

따라서 Grafana 시간과 RunPod 내부 HPE 시간을 직접 비교해서는 안 된다는 결론을 얻었다.

## 7. RunPod 원격 모델 API 구성

RunPod에 FastAPI 서버를 만들고 8000번 포트를 HTTPS 프록시로 노출했다.

```text
OCI
→ HTTPS
→ RunPod 8000번 프록시
→ 모델을 한 번 적재한 GPU API
→ 포즈 JSON 반환
```

공개 포트이므로 공유 토큰으로 요청을 인증했다. Jupyter용 8888번과 GPU API용 8000번은 서로 다른 용도다.

500프레임 시험에서는 OCI→RunPod→OCI 왕복 13.598초, RunPod 내부 처리 8.484초를 기록했다.

동일한 136프레임 원본을 사용한 시험은 다음과 같았다.

| 구간 | 시간 |
|---|---:|
| OCI CPU 자세 추론 | 16.737초 |
| OCI→RunPod→OCI 왕복 | 5.282초 |
| RunPod 내부 요청 처리 | 1.880초 |
| 순수 감지+자세 추정 | 1.693초 |

자세 추론 구간과 원격 왕복을 비교하면 68.4% 감소, 약 3.17배 향상이었다. 네트워크와 직렬화 비용은 약 3.4초였다.

## 8. 임시 사이트 A/B 비교

운영 코드에 영구 반영하지 않은 임시 분기로 분석 이름에 따라 CPU와 RunPod 경로를 선택하는 시험을 진행했다.

| 구간 | OCI CPU | RunPod 추론 | 감소 |
|---|---:|---:|---:|
| 프레임 추출 | 10.31초 | 10.29초 | 거의 없음 |
| 사람 검출·자세 추론 | 13.62초 | 6.35초 | 53.4% |
| 렌더링·영상 합성 | 26.08초 | 26.71초 | 없음 |
| 특징 계산 | 2.04초 | 2.06초 | 없음 |
| LLM 리포트 | 23.76초 | 24.95초 | 없음 |
| 전체 처리 | 76.56초 | 70.91초 | 7.4% |

이 결과는 추론만 GPU로 이동하면 전체 서비스 개선이 제한적이라는 사실을 보여줬다. 임시 분기는 이후 공식 Worker 재배포로 사라졌으며, 분석 이름만으로 GPU 실행 여부를 판단해서는 안 된다.

## 9. 결과 정확도 비교

초기 고정 입력에서는 CPU와 GPU 모두 78개 결과 프레임을 만들었고 누락 프레임과 인원수 차이가 없었다.

```text
전체 관절 평균 차이: 약 0.143px
신뢰도 0.5 이상 평균 차이: 약 0.129px
신뢰도 0.5 이상 최대 차이: 약 12.57px
```

이는 평균적으로 매우 유사하지만 피처 영향 검사가 추가로 필요하다는 뜻이다.

## 10. 긴 영상 탐색 시험

약 36~38초로 기록된 720p·30fps 영상에서 CPU 1회와 GPU 2회를 비교했다. 정확한 원본 길이 표기가 기록마다 달라 탐색 자료로만 보존한다.

| 구간 | CPU | GPU 1차 | GPU 2차 |
|---|---:|---:|---:|
| 자세 추론 | 111.72초 | 21.30초 | 19.29초 |
| LLM 리포트 | 12.63초 | 15.79초 | 25.67초 |
| 전체 | 246.50초 | 158.99초 | 167.90초 |
| LLM 제외 | 233.87초 | 143.20초 | 142.23초 |

긴 영상에서는 GPU 추론 효과가 더 크게 드러났지만 리포트 시간 변동과 입력 길이 기록 불일치가 있어 최종 기준값으로 사용하지 않는다.

## 11. 피처 관련 반복 실패

여러 영상에서 다음 오류를 확인했다.

| 오류 | 건수 | 직접 원인 |
|---|---:|---|
| `ZeroDivisionError` | 5 | stride 목록이 비었는데 개수로 나눔 |
| `AssertionError` | 4 | 최대·최소 이벤트가 교대로 검출되지 않음 |
| `IndexError` | 1 | 전환점 목록이 비었는데 첫 항목 접근 |
| `ValueError` | 1 | NaN을 포함한 리포트 JSON 저장 실패 |

이 문제는 GPU 성능과 별개인 입력·피처 강건성 문제다. 최신 피처가 완성되지 않았으므로 모델 골든 품질 승인은 아직 대기 상태다.

## 12. 파이프라인 변경

후속 배포에서 9개 단계가 6개 상위 단계로 바뀌고, 프레임 추출·추론·렌더링·인코딩이 `video_analysis`로 합쳐졌다. 과거 9단계 수치와 최신 6단계 수치를 같은 단계인 것처럼 직접 비교할 수 없다.

## 13. CPU 영상 경로 개선

중간 OpenCV `mp4v` 영상 생성과 후속 H.264 재인코딩을 제거하고, 렌더링 프레임을 FFmpeg `libx264 veryfast CRF23`으로 직접 전달했다.

이 시험은 당시 운영 Worker 이미지 `sha-d3753fc9...`의 격리 복사본에서 수행했다. 2026-09-07 운영 이미지는 `sha-6743f353...`로 바뀌었지만 HPE 실행 내용과 ONNX 가중치 해시는 같다고 확인했다.

| 입력 | 기존 CPU | 개선 CPU | 단축 |
|---|---:|---:|---:|
| 720p·60fps·4.25초 | 16.876초 | 12.670초 | 24.92% |
| 720p·29.97fps·21.05초 | 83.351초 | 73.965초 | 11.26% |

기존과 개선 CPU의 자세 예측 JSON 해시는 완전히 같았다.

## 14. 전체 영상 분석 GPU 격리 검증

OCI에서 고정 영상을 RunPod RTX 2000 Ada API로 보내고, CUDA 분석과 NVENC 인코딩 후 결과를 다시 받는 전체 왕복시간을 두 번 측정했다.

| 입력 | 기존 CPU | 개선 CPU | GPU 왕복 | 기존 CPU 대비 GPU |
|---|---:|---:|---:|---:|
| 720p·60fps·255프레임 | 16.876초 | 12.670초 | 8.773초 | 48.01% 단축 |
| 720p·29.97fps·631프레임 | 83.351초 | 73.965초 | 17.461초 | 79.05% 단축 |

GPU 반복 실행 두 번은 동일한 예측 해시를 생성했다. 60fps 입력은 CPU/GPU 프레임과 인원수가 같고 평균 관절 차이는 0.1425px였다. 29.97fps 입력은 631프레임 중 349번 프레임에서 CPU 2명, GPU 1명으로 달랐으며 일부 관절에 큰 이상치가 있었다.

이 결과는 운영 사이트가 아니라 운영 이미지와 별도 RunPod API를 사용한 격리 시험이다.

## 15. 최신 모델 배포 추적

모델 전달 관계를 다음과 같이 확인했다.

```text
모델 담당자 Oracle_Project 커밋 dcc2d7d...
→ Runners_Feed 통합 커밋 ed8eeb...
→ OCI Worker 이미지 태그 sha-6743f353...
```

최신 명세, OCI 호스트, Worker가 보는 두 ONNX 해시는 모두 일치했다. OCI에는 `sehyeon-dcc2d7d` 플러그인이 포함됐지만 품질 승인이 대기 중이어서 기본 HPE·피처·리포트 진입점을 유지한다. 기본 HPE와 플러그인 HPE, 기본 피처와 플러그인 피처는 공백을 제외하면 동일하다. 리포트 코드는 실행 인자와 LLM 설정이 달라 정식 전환 전 검토가 필요하다.

## 16. 현재 결론

- GPU가 ONNX 추론을 크게 가속한다는 사실은 여러 범위의 시험에서 반복 확인했다.
- 추론만 원격 GPU로 옮긴 사이트 시험의 전체 개선은 7.4%로 제한적이었다.
- 렌더링·인코딩까지 포함한 최신 격리 시험에서는 전체 `video_analysis`가 48.01~79.05% 단축됐다.
- 짧은 영상에서는 약 5초의 네트워크·응답 준비 비용 비중이 크다.
- 29.97fps 입력의 CPU/CUDA 경계 결과 차이는 미해결이다.
- 최신 피처와 골든 품질 승인이 완료되기 전에는 모델 플러그인을 운영에 강제 적용하지 않는다.
- 운영 적용과 Grafana 최종 검증은 조장 승인 후 공식 배포 절차로 수행해야 한다.

## 17. 정식 통합을 위한 처리 경계 재확인

팀 저장소 로컬 체크아웃 `8a2ac7f`에서 피처·리포트·스켈레톤·결과 영상 소비 경로를 읽었다. 현재 후처리는 `pose_predictions.json`, `details.json`, `user_info.json`을 사용하며 결과 MP4를 다시 렌더링하지 않는다. 따라서 RunPod은 검출·자세 추정·추적·렌더링·NVENC까지의 `video_analysis`를 맡고, OCI는 피처·리포트·스켈레톤 어댑터를 수행하는 경계를 후보로 정했다. 실행 중인 OCI와 원격 최신 버전 일치는 배포 전에 다시 확인한다.

## 18. Object Storage 계약 v2

서비스 Job ID와 GPU 시도 ID를 분리하고 입력·모델·소스 해시, 시도별 결과 prefix와 완료 manifest 형식을 정의했다. RunPod은 자세 JSON·영상 정보 JSON·완성 영상을 모두 올린 뒤 manifest를 마지막에 게시한다. OCI는 manifest 문자열만 믿지 않고 요청 일치, 객체 크기·해시, JSON 내용과 영상 메타데이터를 확인한다.

## 19. 후처리 및 RunPod 게시 후보 구현

OCI 후처리 후보는 HPE를 다시 실행하지 않고 feature, 계약 검사, 선택적 Agent, report adapter, skeleton adapter를 호출한다. 완성 영상은 무결성·형식 확인 후 원래 Object Storage 경로를 재사용한다. RunPod 후보는 warm CUDA 엔진과 NVENC를 사용하고 세 산출물 이후 manifest를 게시한다. 입력 손상, CPU provider, 누락 산출물에서는 완료 manifest를 게시하지 않는다.

## 20. OCI dispatcher 후보

OCI Pod transport 후보는 HTTPS Authorization 헤더로 계약 요청을 전달하고, 응답의 Job ID·시도 ID·manifest 경로가 모두 일치할 때만 후처리 대상으로 반환한다. 자동 POST 재시도는 넣지 않았다. DB 상태를 가진 Celery 계층이 현재 시도를 조건부 생성하고 재시도마다 새 attempt ID를 발급해야 한다. 이 시점의 구현은 로컬 단위 시험 20개를 통과했으며 실제 OCI·RunPod·사이트·Grafana 통합 결과는 아니다.

## 21. 팀 DB·Celery 통합 후보와 릴리스 자기검증

격리된 팀 저장소 worktree에 입력 ETag·크기 snapshot, GPU attempt migration, `gpu_dispatch`와 `postprocess` 큐, HPE를 호출하지 않는 후처리 전용 진입점을 연결했다. Worker 테스트 33개와 변경 관련 API DB 테스트 18개, Compose·Python·셸 구문 검사를 통과했다. RunPod API도 시작 시 실제 HPE 소스 3개와 ONNX 2개의 SHA-256을 계산하고 요청의 릴리스 증거와 일치하지 않으면 실행 전에 거부하도록 보강했으며 공개 후보 전체 단위 시험은 21개를 통과했다. 실제 OCI migration, Object Storage 왕복, CUDA 실행, 사이트·Grafana 검증은 아직 수행하지 않았다.

운영 OCI Console 권한이 없는 팀원이 장기 API 키를 RunPod에 복사하지 않도록 인증 경계를 다시 수정했다. 기존 API의 PAR 발급 기능을 이용해 입력 읽기 URL 하나와 결과 객체별 쓰기 URL 네 개를 attempt마다 생성한다. RunPod은 OCI 도메인의 만료 URL만 허용하며 URL을 완료 manifest에 넣지 않는다. 이 변경 후 공개 후보 23개, 팀 Worker 34개, API DB 18개 테스트를 통과했다.

## 22. 운영 사이트 전체 경로 검증

2026-09-08 KST에 팀 저장소 PR #23으로 Object Storage 기반 RunPod 파이프라인을 병합하고, PR #24에서 RunPod 프록시가 허용하는 명시적 User-Agent를 추가했다. 첫 운영 작업 `e903648a-6a3f-4bef-af64-40b330c24a35`는 PostgreSQL UUID를 JSON에 직접 넣어 RunPod 호출 전에 실패했다. PR #25는 계약 경계에서 Job ID와 attempt ID를 문자열로 정규화하고 실제 UUID 객체를 사용한 회귀 시험을 추가했다.

PR #25 병합 커밋 `adc592aabd1032b19dceeb965df89a05c50ec5a3`의 최초 배포는 OCI self-hosted Actions runner의 디스크가 97% 사용 중이어서 중단됐다. 24시간보다 오래된 미사용 Docker 이미지·빌드 캐시와 오래된 runner 진단 로그를 정리해 17GB를 확보한 뒤 재배포했다. 불변 릴리스 배포와 운영 checkout 승격은 성공했고, systemd unit 동기화만 기존 passwordless sudo 미설정으로 실패했다.

같은 720p·60fps 입력을 사이트에서 `runpod-e2e-adc592a`로 다시 실행했다. 작업 `44c9e8f8-2941-4e48-96e3-5a994b9d14c2`는 OCI 업로드, `gpu_dispatch`, RunPod 전체 `video_analysis`, 시도별 Object Storage 산출물·manifest, OCI `postprocess`, DB 완료 상태와 사이트 결과 표시까지 모두 통과했다.

Grafana `Runners Feed / Job Stage Performance`에서 다음 값을 확인했다.

| 항목 | 운영 측정값 |
|---|---:|
| 상태 | SUCCESS |
| 총 처리시간 | 24.6초 |
| 큐 대기시간 | 107.956ms |
| `video_analysis` | 5.8초 |

이 측정으로 후보 구현이 아니라 실제 운영 사이트의 OCI→RunPod→OCI 경로가 끝까지 동작하고 단계 시간이 수집됨을 확인했다. 다만 운영 표본은 아직 1건이므로 성능 분포와 성공률을 판단하려면 같은 입력 반복 및 여러 길이·FPS 입력의 추가 표본이 필요하다.

## 23. 운영 배포 안정화

팀 저장소 PR #26에서 systemd unit 동기화를 멱등화하고 Production 이미지 Pull 전 Docker 디스크 guard를 연결했다. 저장소 unit과 운영 unit이 같고 네 timer가 이미 활성 상태이면 배포 계정이 sudo를 호출하지 않는다. unit이 실제로 바뀌거나 timer가 비활성 상태일 때만 Production 관리자 동기화가 필요하다.

OCI 관리자 동기화 후 다음 timer가 모두 `enabled`와 `active`임을 확인했다.

- `runners-feed-cert-renew.timer`
- `runners-feed-db-backup.timer`
- `runners-feed-db-backup-verify.timer`
- `runners-feed-model-quality-watchdog.timer`

PR #26은 필수 검사 6개를 통과한 뒤 `main` 병합 커밋 `0418518c7844fe6279f8f0761c8ba9c827cf60fe`가 됐다. 해당 릴리스는 이미지 build·test·push, OCI 불변 릴리스 배포, 운영 checkout 승격과 마지막 systemd 동기화까지 모두 성공했다. RunPod API도 같은 `MODEL_RELEASE`로 재기동하고 CUDA health 응답을 확인했다.
