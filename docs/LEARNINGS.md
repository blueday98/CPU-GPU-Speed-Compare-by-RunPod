# 시행착오와 배운 점

## 숫자보다 측정 경계가 먼저다

GPU 순수 추론이 100배 빨라도 서비스 전체가 100배 빨라지는 것은 아니다. 디코딩, 렌더링, 인코딩, 네트워크, 피처, LLM이 남기 때문이다.

## 분석 이름은 실행 장치가 아니다

`gpu_ab`라는 이름은 라우팅 코드가 실제로 존재할 때만 의미가 있다. 배포 후 임시 분기가 사라지면 이름이 GPU여도 CPU로 실행된다. 장치 증거, 공급자, 원격 요청 ID를 함께 기록해야 한다.

## Grafana는 모델을 실행하지 않는다

Worker가 모델을 실행하고 DB에 시간을 저장하며 Grafana는 그 값을 보여준다. 최신 모델 적용 여부는 Grafana 화면이 아니라 이미지 태그, 모델 ID, 진입점, 소스·가중치 해시로 확인한다.

## 파일 날짜보다 해시가 중요하다

OCI ONNX 파일은 8월에 배치됐지만 9월 최신 명세와 해시가 같다. 날짜만 보고 오래된 모델이라고 판단하면 안 된다.

## 컨테이너 직접 수정은 재배포 때 사라진다

실행 중인 Worker에 넣은 임시 GPU 분기는 공식 이미지 재배포로 없어졌다. 재사용할 변경은 코드 저장소, 이미지 빌드, 검토 가능한 배포 절차에 포함해야 한다.

## RunPod 영구 볼륨과 프로세스는 다르다

Pod를 멈췄다가 켜면 영구 볼륨의 모델과 가상환경은 남아도 API 프로세스는 다시 시작해야 한다. 외부 포트 주소와 SSH 접속 정보도 바뀔 수 있다.

## 짧은 영상은 네트워크 비용에 민감하다

4.25초 영상의 GPU 내부 분석과 NVENC는 약 3.7초였지만 전체 왕복은 8.77초였다. 긴 영상에서는 GPU 계산 절감이 전송 고정비보다 커져 효과가 더 커졌다.

## 정확도는 평균만 보면 안 된다

평균 관절 오차가 작아도 한 프레임의 인원수 차이나 큰 관절 이상치가 피처에 영향을 줄 수 있다. 프레임 누락, 인원수, 백분위, 최대값, 임계값 초과 개수를 함께 본다.

## 피처 실패는 성능 실패와 분리한다

stride가 없거나 이벤트 검출이 실패하는 문제는 GPU 속도와 다른 문제다. 실패 입력을 억지로 성능 평균에 포함하지 않고 별도 Issue와 회귀 테스트로 관리한다.

## 운영 적용과 기술 검증을 구분한다

격리 시험은 기술적 가능성을 증명한다. 사이트·Grafana 결과라고 주장하려면 공식 배포, 실제 라우팅 증거, 동일 입력의 새 Job이 필요하다.
